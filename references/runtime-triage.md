# 运行时排障手册

`scripts/agent-diag.js` 的取证口径与误判说明。只覆盖 Agent 与 Skill 基础设施层。

## 0. 通用约定

- 四种模式：`drift`、`engine`、`mcp`、`loop`，一次只跑一种。
- 输出固定四段：问题分类 → 根因定位 → 修复建议 → 回归验证步骤；`--json` 输出同一结构。
- 退出码：0 未发现问题，1 发现问题，2 参数或文件错误（可直接接 CI）。
- 所有结论必须带证据：步骤号、相似度、端口、变量名、重复次数。没有证据的假设只能写成「待验证」。

## 1. Skill 行为漂移（drift）

输入两份运行结果：

```json
{
  "name": "prism-qa",
  "version": "1.5.0",
  "engine": "claude-code",
  "cases": [{ "id": "C1", "input": "给登录框设计用例", "output": "..." }]
}
```

判定：

- 按 `id` 对齐；缺失用例直接记为「覆盖退化」。
- 文本归一化（去空白）后计算字符 bigram Dice 相似度，`<0.85` 记为漂移。
- 版本号不同会单独列为根因候选，但不作为漂移的充分条件。

误判与处理：

- 合理改写（同义句、顺序调整）也可能低于阈值：报告必须提示「需人工确认语义是否等价」，不得直接判定为缺陷。
- 输出很长时相似度对局部变化不敏感：可配合结构校验（字段是否齐全）一起看。
- 阈值可按场景调整：`--threshold 0.9` 更严，适合结构固定的场景。

根因树（按顺序排查）：

1. 全部用例漂移 → 模型版本、系统提示、全局参数变更。
2. 部分漂移 → 这些用例涉及的输入分支、工具、依赖数据。
3. 输出变短或为空 → 上下文截断、超时、异常被吞。
4. 输出结构变 → 提示词里的输出约束被改动或丢失。

## 2. 跨引擎不一致（engine）

输入两侧结果，字段：`id / pass / output / toolCalls`。

判定优先级：

1. `pass` 不同 → 判定不一致（优先怀疑判定脚本与阈值，而不是模型）。
2. 都通过但输出相似度 `<0.85` → 输出不一致（怀疑采样参数、上下文窗口、工具描述）。
3. `toolCalls` 不同 → 工具选择差异（预警级，不一定阻断）。

处理原则：判定逻辑必须统一到一份脚本，两个引擎只负责产出。差异样本登记进跨引擎回归集，并标注「允许差异」的判定标准，否则回归会一直红。

## 3. MCP 调用失败（mcp）

配置格式（兼容 `mcpServers` 与 `servers`）：

```json
{
  "mcpServers": {
    "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."], "env": { "ROOT": "${PWD}" } },
    "remote": { "url": "http://127.0.0.1:8080/mcp", "headers": { "Authorization": "Bearer ${TOKEN}" } }
  }
}
```

检查顺序（与客户端启动顺序一致）：

1. `command` 是否存在（Windows 用 `where`，类 Unix 用 `which`）。不存在 → 启动即失败。
2. `env` 里的 `${VAR}` 是否在当前进程可见。不可见 → 握手或鉴权失败，报错往往与「未授权」相似，容易误判为密钥错误。
3. 远程 `url` 的 host:port 是否 TCP 可达（默认 2s 超时）。不可达 → 服务未启动、端口错、网络或白名单问题。
4. 配置中是否有明文凭据（Bearer/sk- 前缀）。有 → 记为安全问题并脱敏展示，建议轮换。

常见误判：

- 端口通但工具列表为空：不是网络问题，查握手、工具重名、客户端是否重启。
- 变量在终端里有、在 GUI 客户端里没有：GUI 不继承 shell 环境，必须写进客户端配置或系统环境。
- `npx` 能找到但启动超时：首次下载依赖，属正常，第二次再判。

## 4. Agent 死循环（loop）

输入 JSONL，一行一个事件：

```json
{"step":1,"tool":"search","args":{"q":"order 1001"},"output":"找到 1 条订单记录"}
```

检测信号：

| 信号 | 阈值 | 说明 |
| :--- | :--- | :--- |
| 步数超限 | `--max-steps`，默认 40 | 正常任务一般 <20 步 |
| 同工具同参数重复 | `--repeat`，默认 3 | 参数用 JSON 序列化后比较 |
| 往复循环 | A→B→A→B 出现一次 | 两类工具来回切换 |
| 输出无进展 | 同一输出重复 3 次 | 说明没有获得新信息 |
| 错误原样重试 | 错误事件 ≥3 次 | 未改变策略或参数 |

误判与处理：

- 合理轮询（等待任务状态）会命中「重复调用」：要求事件里带 `reason=polling` 或轮询间隔时，应在报告中标注为「疑似合理轮询」，不要直接判缺陷。
- 多步任务本身步数多：先看是否每步都有新信息，再看步数。
- 失败重试是正常策略：关键在「是否改变参数/工具」「是否有上限」。

修复优先级：

1. 提示层写终止规则（什么算完成、什么算失败、失败几次停）。
2. 运行时加最大步数、预算、超时三层限制。
3. 工具返回带区分度信息（「无结果」要说明原因）。
4. 失败后强制换参数或换工具，仍失败则中止并回报。

## 5. 与 skill-up 的分工

- skill-up：YAML 定义用例、多引擎执行、CI 集成，输出每个用例的执行结果。
- 本脚本：不重复执行，只做结果比对与判定（漂移、跨引擎差异、循环），输出带证据链的报告。
- 串联方式：skill-up 跑完后把结果整理成本文第 1、2 节的 JSON 格式，再交给 `agent-diag`；两步之间不需要改 skill-up 本身。

## 6. 边界声明

本模块只做 **Agent 与 Skill 基础设施层**：行为漂移、跨引擎差异、MCP 接入、循环与终止。

不做：应用卡死、JS/C++ 崩溃、内存泄漏、CPU 火焰图、端到端性能分析。这些问题由鸿蒙 DFX Skills v1.3.0 覆盖，且做得更深；本 Skill 与其互补，不重复实现。

## 7. 报告模板

```
问题分类：Skill 行为漂移
证据：C3 相似度 0.43（阈值 0.85）；版本 1.4.0 → 1.5.0
根因定位：版本升级改动了系统提示；输出从 10 条降到 3 条
修复建议：对比两版提示词并二分回滚；给输出加结构校验
回归验证：恢复基线配置重跑 4 条用例，相似度 ≥0.85 且连续 3 次稳定
```
